# Hotel Bar Inventory Forecasting and Recommendation

## Project overview

This project uses historical inventory movement records to help bar managers anticipate demand, set practical stock targets, and reduce stockouts without holding excessive inventory.

- main.ipynb contains the analysis, backtest, and inventory simulation.
- inventory_recommendations.csv is generated by the notebook and contains 96 bar-brand recommendations.
- inventory_insights_report.md summarizes the findings and assumptions.
- requirements.txt lists the packages used by the notebook.

## End-to-end pipeline

1. **Load and check the source.** The notebook reads the CSV, validates required columns, parses timestamps, and converts movement values to numbers. It checks missing values, invalid timestamps, exact duplicates, negative quantities, and the difference between recorded closing balance and opening balance plus purchases minus consumption. Suspect rows are flagged; the source file is not edited or silently corrected.
2. **Prepare demand data.** Rows are grouped by bar, alcohol type, brand, and calendar date. Negative-consumption rows are reported and excluded from demand analysis. Multiple rows on one date are summed. Missing item-days are filled with zero recorded demand to create a daily series, and record coverage is shown for each combination.
3. **Explore the history.** Charts compare recorded consumption by alcohol type and bar. These are recorded totals and may reflect different logging coverage.
4. **Compare two forecasts.** An eight-week moving average is compared with a previous-week baseline using chronological rolling validation. MAE, WAPE, and bias are reported.
5. **Select a forecast and calculate stock targets.** The method with the lowest WAPE is selected; MAE breaks a tie. If validation demand is zero and WAPE is undefined, MAE decides. The selected method is used for the final forecast and recommended policy.
6. **Simulate replenishment.** A fixed baseline policy is compared with the forecast-and-safety-stock policy on the same historical demand sequence. Orders arrive only on their scheduled dates; unmet demand is treated as lost sales.
7. **Prepare manager outputs.** The notebook displays recommendations and charts, then exports forecast, par, stock-validity, and policy-assumption fields to inventory_recommendations.csv.

## 1. Core business problem and why it matters

A bar that runs out of a popular brand can disappoint guests and lose sales. Holding too much slow-moving stock ties up cash and increases the chance of waste, expiry, or breakage. Demand differs by location, so managers need recommendations for each bar and brand rather than chain-wide totals.

Par is the target amount to keep available. The reorder point is the inventory position at which replenishment should begin. In the simulation, inventory position means on-hand stock plus open orders. Suggested order quantity is the amount needed to reach par, provided the stock position passes the notebook's validity checks.

## 2. Assumptions and why they were made

- **Missing dates are treated as zero recorded use.** A regular daily series is needed for weekly forecasting and simulation. This is only an assumption: a missing row may mean zero activity or incomplete logging. Average recorded-day coverage is 18.7%, so this limitation is substantial.
- **Lead time is 3 days, review interval is 7 days, and service level is 95%.** These are configurable examples because supplier timing and management targets are not in the file.
- **Planning quantities are rounded up to 50 ml.** This provides a simple nonnegative planning increment. Bottle and case pack sizes are unavailable, so managers must convert the target into purchase units.
- **A balance discrepancy over 1 ml is flagged.** This is a screening tolerance, not an accounting standard. In this file, 86 rows exceed it; the largest absolute discrepancy is 9.25 ml. The rows remain visible for review.
- **Negative consumption is excluded if found.** It cannot be used as ordinary demand. The notebook reports it instead of silently changing it to zero. No negative quantities were present in this file.
- **Simulation shortages are lost sales, not backorders.** The data does not say whether guests wait or substitute another drink.
- **Both policies start with the same modeled stock.** Initial stock uses each item's average daily demand in the first eight training weeks multiplied by the ten-day protection period, rounded up to 50 ml. This provides a shared starting point where a complete opening-stock snapshot is unavailable.
- **Costs are not estimated.** Purchase prices, carrying costs, waste costs, and lost-sale penalties were not supplied.
- **Historical balances are not current stock.** The file ends on 1 January 2024. Suggested order quantity is populated only when an item's latest record is on that date and has a nonnegative, nonduplicate, balance-consistent position within the 1 ml tolerance. Only 17 positions pass; even these require a current stock check before ordering.

## 3. Forecast model and why it was selected

The notebook retains two simple methods:

1. **Eight-week moving average:** average the previous eight complete weekly demand totals.
2. **Previous-week baseline:** use the immediately preceding complete week's demand.

Validation uses the first eight weeks after an eight-week warm-up. Each weekly prediction uses only earlier weeks. The selected method is therefore available before the simulation starts.

Across 768 item-weeks, the eight-week average scored **325.1 ml MAE, 85.4% WAPE, and +4.8% bias**. The previous-week baseline scored **389.5 ml MAE, 102.3% WAPE, and +0.1% bias**. The eight-week average was selected because it had lower WAPE and MAE. The baseline had slightly less bias, but substantially larger total error.

More complex models were not added. The file covers about one year, and each bar-brand combination has only about 68 recorded days on average. Missing records are a bigger concern than model complexity. Seasonal, weekday, or machine-learning models would be difficult to validate reliably with these sparse series. With complete daily data, those effects could be tested against the current baselines.

## 4. Par calculation and system performance

**Protection period = supplier lead time + review interval**

The expected daily demand is the selected weekly forecast divided by seven.

**Reorder point = expected demand during lead time + safety stock**

**Par level = expected demand during the full protection period + safety stock**

Safety stock is the service-level z-score multiplied by the recent daily demand standard deviation and the square root of the protection period. Par and reorder point are rounded up to 50 ml.

The historical simulation covers **253 days per item**, from 24 April 2023 through 1 January 2024, across 96 item combinations. The baseline uses a fixed order-up-to target based on the initial training average and no safety stock. The recommended policy uses the selected forecast based only on completed weeks available at each review, adds safety stock, and orders toward par when inventory position reaches reorder point. Both policies review weekly and use the same lead time and starting-stock assumption.

| Simulation measure | Baseline | Recommended |
|---|---:|---:|
| Stockout days across item-days | 1,838 | 375 |
| Unmet demand (ml) | 467,927.2 | 85,360.2 |
| Average total inventory (ml) | 33,412.2 | 93,590.4 |
| Replenishment orders | 1,479 | 1,569 |
| Ordered volume (ml) | 865,384.4 | 1,324,816.4 |
| Turnover over simulation period | 26.2 | 13.4 |

Under these assumptions, the recommended policy had fewer stockout item-days and less unmet demand, while holding more average inventory and ordering more volume. This is a service-versus-stock trade-off, not proof of financial savings or a guarantee of future performance. No costs are estimated because the dataset has no price, waste-cost, or stockout-penalty fields.

## 5. Improvements to make next

The highest-value improvement is better data coverage. Record daily sales or consumption by bar and item, including days with no use, and reconcile purchases, transfers, breakage, and closing counts. Then:

- Re-evaluate forecast error by bar, item, weekday, and season.
- Add holidays, local events, occupancy, and promotions when available.
- Set lead time, service level, pack size, and minimum order by supplier and item.
- Collect stockout, substitution, waste, expiry, and delivery records.
- Test whether the par rule balances service with real inventory and waste costs.

## 6. How this would work in a real hotel

A point-of-sale or inventory system would send daily item movements and current stock for every bar. At each review, the system would update demand using information available at that time, add open purchase orders to on-hand stock, and compare inventory position with reorder point. It would alert the manager with the item, bar, forecast, par, suggested purchase packs, and data timestamp. A manager would verify the stock count and approve or adjust the order. Deliveries, stockouts, waste, and overrides would feed back into monitoring.

## 7. What could break at scale and what to monitor

The current workflow is a local notebook over a CSV. It relies on consistent column names, manual file placement, one shared set of assumptions, and sparse records that are zero-filled. At many properties and thousands of item-days, building a full item-by-calendar grid can use substantial memory. Renamed bars, new brands, partial feeds, duplicate imports, time-zone differences, transfers, and stale stock updates can also produce bad recommendations. A production service would need reliable ingestion, stable item and location identifiers, per-supplier settings, scheduled processing, audit logs, access controls, and alert handling. Those infrastructure pieces are outside this assignment.

Monitor data completeness and balance discrepancies, forecast MAE/WAPE/bias, stockout item-days, unmet demand, fill rate, average inventory, replenishment volume, actual delivery lead times, waste/expiry, and manager overrides. Review these by bar and item so a chain-wide average does not hide a local problem.

## Running the notebook

Install the packages listed in requirements.txt, open main.ipynb, and run cells from top to bottom. The notebook checks the original Downloads location, the notebook folder, and a data subfolder for the CSV. Update DATA_PATH in the setup cell if the file is elsewhere. Running the final cell refreshes inventory_recommendations.csv.
